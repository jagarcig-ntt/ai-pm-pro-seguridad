Git profesional

Ramas, commits con sentido y el Pull Request como punto de control.

Caso Google Cloud · junio de 2025
Antes de entrar
→Repositorio: la carpeta de tu producto con memoria.
→Rama: un borrador del documento, en lugar de editar el original.
→Pull Request: pedir que acepten tus sugerencias antes de que entren.
Tres ideas
1La rama: main siempre funciona. Todo cambio se hace aparte. Con main protegida, Lovable guarda tus cambios en la rama lovable-sync.
2El commit con sentido. Lovable firma "Changes" o "Work in progress": no eliges esos mensajes, pero sí el título y la descripción de tu Pull Request.
3El Pull Request es tu punto de control. Las dos preguntas de un PM: ¿qué pasa si falla? ¿Cómo se apaga?
Así fluye cada cambio
Caso real · Google Cloud, junio de 2025

Un código nuevo sin manejo de errores ni interruptor para apagarlo. Un dato vacío lo activó y el servicio cayó en todo el mundo durante varias horas. Según el informe de Google, con un interruptor se habría detectado antes.

Lo que el PM se lleva

main siempre funciona · La historia de cambios es el diario del producto · Antes de aprobar, pregunta qué pasa si falla y cómo se apaga.

Entornos y secretos

Dónde se prueba, dónde se cobra y dónde viven las claves.

Caso Replit y SaaStr · julio de 2025
Antes de entrar
→Entorno: cada sitio donde vive una copia de tu producto.
→Variable de entorno: un ajuste que cambia según el sitio, sin tocar el código.
→Secreto: una llave que, si alguien la tiene, actúa en nombre de tu producto.
Tres ideas
1Tres entornos: development es la vista previa de Lovable; staging, la preview de cada Pull Request; producción, la URL de tu Worker. La vista previa de Lovable no es staging: corre en otro sitio. En tu producto, los tres comparten la base de datos.
2La misma app, distinta configuración. El .env que sube Lovable es público: solo lo que podrías publicar en tu web.
3Los secretos viven en la plataforma. Nadie puede leerlos una vez guardados, ni siquiera tú.
Tus tres entornos, tus datos y tus secretos
Caso real · Replit y SaaStr, julio de 2025

En plena congelación de código, el agente de Replit borró la base de datos de producción de SaaStr. Una instrucción no es una barrera; un entorno separado, sí.

Nos pasó preparando esta sesión

Al aprobar en Lovable un cambio de login, se cambiaron los permisos de la base de datos en el momento, antes de cualquier Pull Request, y la web publicada se cayó. La rama protege el código, no los datos. Lee el SQL antes de pulsar Allow.

Lo que el PM se lleva

Probar y cobrar no se hacen en el mismo sitio, y si lo compartes, que sea a sabiendas · El código es el mismo y la configuración cambia · Los secretos, en la plataforma.

CI/CD y despliegue

La receta automática que comprueba y publica cada cambio.

Caso CrowdStrike · julio de 2024
Antes de entrar
→CI: el control de calidad automático que no se cansa.
→CD: la publicación automática; nadie tiene que acordarse de "subirlo".
→Workflow: la receta escrita de ese proceso.
Tres ideas
1El workflow, una receta que se ejecuta sola: coge el código, lo instala, pasa las pruebas, lo compila, lo publica y comprueba que la web responde.
2Cada Pull Request se comprueba y se previsualiza. En rojo no se puede hacer merge, y ni siquiera se publica la preview.
3Hacer merge es decidir salir a producción, y la salida avanza por fases.
Caso real · CrowdStrike, 19 de julio de 2024

Una actualización esperaba 20 campos y recibió 21. Llegó a la vez a todos los equipos: Microsoft estimó 8,5 millones de dispositivos Windows bloqueados. Automatizar sin fases convierte un error en un error para todos a la vez.

Nos pasó preparando esta sesión

Lovable escribió código que no compilaba porque olvidó añadir una dependencia. Con main protegida y este control, un fallo así no llega a tus usuarios.

Lo que el PM se lleva

El proceso de calidad es una receta escrita · Ningún Pull Request entra en rojo · Hacer merge es decidir salir a producción.

Go-live y recuperación

Decidir salir y saber volver.

Caso Sonos · mayo de 2024
Antes de entrar
→Go-live: abrir la puerta a los usuarios; una decisión de negocio.
→Rollback: el botón de deshacer de producción.
→Monitorización: el cuadro de mandos del coche.
Tres ideas
1Salir es una decisión, con una checklist de 8 preguntas. Está en el kit.
2El plan de vuelta atrás se conoce antes de salir. Rollback para recuperar el servicio ya; revert para dejar el código bien. Los cambios de base de datos no se deshacen con un rollback.
3Después de salir, vigila tres señales: errores, rendimiento y uso. La tercera la ve sobre todo el PM.
Caso real · Sonos, mayo de 2024

Lanzaron una app rediseñada sin funciones que la gente usaba a diario y no pudieron volver a la anterior. Según la compañía, arreglarla costó entre 20 y 30 millones de dólares. Su CEO: "nuestra ejecución, mi ejecución, se quedó corta".

Nos pasó preparando esta sesión

Pruebas, compilación y publicación en verde, y la web daba error 500. Verde no significa que funcione. Por eso tu workflow comprueba al final que la web responde, y por eso tú la abres después de cada salida.

Lo que el PM se lleva

Salir es una decisión, con una checklist · El plan de vuelta atrás se conoce antes de salir · El go-live termina cuando sabes que va bien.

Práctica 2 · 12:10 · 45 min

Tu primer cambio por Pull Request

Paso 1 · Protege main

Tres trampas: viene en Disabled (cámbialo a Active) · sin rama no protege nada (Include default branch) · en métodos de merge, solo Merge.
  1. En GitHub: Settings → Rules → Rulesets → New ruleset → New branch ruleset.
  2. Ruleset Name: main siempre funciona. Enforcement status: Active.
  3. Target branches: Add target → Include default branch.
  4. Marca:
    • Restrict deletions;
    • Require a pull request before merging, y dentro, en Allowed merge methods, solo Merge;
    • Require status checks to pass: Add checks y escribe Comprobar el PR, aunque no aparezca en la lista;
    • Block force pushes.
  5. Pulsa Create.
✅ En el chat de Zoom: escribe "Active".

Pasos 2 a 5

  1. Pide un cambio en Lovable, pequeño y visible. El aviso "Some changes were saved on a sync branch" no es un error: es tu protección funcionando.
  2. Abre el Pull Request con esta dirección (pon tus datos), pulsa Create pull request y rellena la plantilla, sobre todo ¿Qué pasa si falla? y ¿Cómo se apaga?
https://github.com/<usuario>/<repo>/compare/main...lovable-sync
✅ En el chat de Zoom: pega el enlace de tu Pull Request.
  1. Revisa antes de aprobar. Checks en verde, abre la URL de preview del comentario y prueba tu cambio como un usuario.
  2. Haz el merge con Create a merge commit, nunca Squash ni Rebase. Si GitHub ofrece Delete branch, no lo uses: Lovable reutiliza lovable-sync. Espera a Desplegar en verde y abre tu producción. En Lovable debe decir In sync with GitHub.
✅ En el chat de Zoom: escribe "producción".

Kit · para el lunes

El ciclo de cada cambio

  1. Pides el cambio en Lovable. Se guarda en lovable-sync.
  2. Abres un Pull Request y rellenas la plantilla.
  3. Checks en verde y preview probada, haciendo lo principal de tu producto.
  4. Merge con Create a merge commit. No borres lovable-sync.
  5. Abres tu web de producción. Verde no significa que funcione.
Base de datos: Lovable aplica los cambios al pulsar Allow, antes del Pull Request. Lee el SQL antes de aprobar; y si borra o cambia permisos, termina el ciclo enseguida.

Checklist de go-live

#Pregunta antes de salir
1¿Lo que sale ha pasado por un PR revisado, con checks en verde?
2¿Se ha probado en la preview del PR, con el flujo principal de usuario de principio a fin?
3¿Están configuradas en producción todas las variables y secretos que necesita?
4¿Cambia algo en la base de datos? Si es así, ¿se puede deshacer?
5¿Sabemos cómo volver atrás y cuánto se tarda?
6¿Hay forma de apagarlo sin cambiar el código (feature flag)?
7¿Alguien estará mirando las señales durante la primera hora tras salir?
8¿Saben soporte y los usuarios afectados lo que cambia?
